# IM Chat Bridge for DeepSeek Harness — Design

Date: 2026-08-17
Status: Draft for review

## 1. Goal & Success Criteria

Build a plugin that bridges **DeepSeek Harness (DSH)** agents onto three IM
platforms — **Matrix, Feishu (飞书), and WeChat (微信)** — so that:

- A user talks to their DSH agent **inside the IM** (inbound message → agent →
  reply routed back to the same conversation).
- Sessions are **isolated per (platform, account, chat/peer)** — reusing DSH's
  own per-session agent+loop machinery, which is the real "联通/接入" value.
- It installs and runs on a **personal always-on machine**, as a DSH **profile**
  (like the built-in `web`/`headless` profiles), not inside the bundled web app.

Success criteria (S1–S6):

- S1 WeChat: can `QR-login`, long-poll `getUpdates`, and send text replies.
- S2 Feishu: bot API with appId/appSecret, long-connection gateway, text replies.
- S3 Matrix: appservice registration acquires a usable room handle; text replies.
- S4 Reply results carry a **fail-safe**: long model turns do not lose the
  user; errors surface in-chat.
- S5 Deterministic per-conversation session mapping; no cross-talk.
- S6 Documented `dsh` CLI usage + a headless single-turn demo + unit tests.

Explicitly out of scope: IM↔IM forwarding, rich media on all platforms (only
text for now; WeChat images/videos are close follow-ups), Web UI.

## 2. Architecture

```
┌─ DSH core (existing) ─────────────────────────────┐
│  agents (AgentRegistry)   agent-loop   sessions   │
│  ctx.agents / ctx.sessions / ctx.get("loader")    │
└───────────────────────────────────────────────────┘
        ▲ followup(msg) / whenIdle() / session deriv
        │
┌─ imchat plugin (node-only Cordis plugin) ─────────┐
│  per-conversation AgentDriver   ▸ bridge core     │
│  message bus (add/consume)      ▸ send replies    │
│  adapters: wechat | feishu | matrix              │
└───────────────────────────────────────────────────┘
```

DSH's `AgentLoop` is *inside* the harness; the headless runner shows the exact
direct-drive recipe: `agents.create(...)` + `installModelSelection(...)` +
`followup(userMessage)` + `whenIdle()` + flush. Our plugin replicates that for
a **long-lived** set of per-conversation agents instead of one-off.

### Adapter responsibilities

Each adapter implements a narrow, protocol-specific surface:

```ts
interface Adapter {
  start(ctx, config): Promise<void>
  stop(): Promise<void>
  onMessage(handler): void   // external → bridge
  send(dest, text, replyTo?): Promise<void>
  sendTyping?(dest, active): Promise<void>
}
```

The bridge core never sees platform protocols; it only knows `dest` strings.

### WeChat (ilink official protocol)

*Source: Tencent openclaw-weixin (MIT) — adapted, not copied wholesale; only
protocol wire shapes are reused, no OpenClaw-isms.*

- QR login: `get_bot_qrcode` → display as terminal QR → poll
  `get_qrcode_status` → capture `bot_token` + `baseurl` (with
  redirect handling).
- Message loop: `getUpdates` long-poll (35s), returns `get_updates_buf` +
  `msgs`; each msg must save `context_token` keyed by sender id and echo it
  verbatim in every outbound `sendMessage`.
- Outbound: `sendMessage` text item; media via `getuploadurl`+CDN (follow-up).
- `-14` stale token: pause 1h and drop; `notifyStart/notifyStop` on lifecycle.

### Feishu (官方机器人 API)

- Config: `appId` + `appSecret` (customer-service account or interactive bot).
- Long connection per 飞书 docs: `getTenantAccessToken` via
  `api.feishu.cn` OAuth; long-connection handshake `wss://` → event push for
  `im.message.receive_v1`; echo throughput.
- Optionally also support webhook mode for max simplicity.

### Matrix (AppService)

- Config: `homeserver` URL, `asToken`, registration file (`*-registration.yaml`)
  generated by `dsh imchat matrix register`.
- Namespaced user/room aliases map to per-sender conversations; transaction
  delivery over `PUT /_matrix/app/v1/transactions/<txnId>`.
- Fallback plan documented: native long-connection bot via `matrix-js-sdk` for
  simpler setups that don't want an appservice.

## 3. Data flow & validation rules

- Inbound msg → normalized `{ platform, account, conversationKey, text, sender }`
  → bridge maps `conversationKey` → agent (create on first sight) →
  `agent.followup(userMessage)`.
- One **bounded** concurrent-turn guard per agent: if a turn is already
  running, append to per-agent queue (no unbounded inbox growth).
- Reply: on `whenIdle` for that turn, take the last assistant text, and `send`
  back with `context_token`/channel reply plumbing.
- Big text: WeChat/Feishu limit length per message → chunker; errors → in-chat
  error notice. All platform calls time-bounded.
- Session mapping is deterministic: `sha1(platform|account|conversationKey)`
  prefix to fit DSH 64-char session-id contract.

## 4. Failure modes

| Mode | Behavior |
|---|---|
| Model call fails | error notice back into the same conversation |
| Platform offline / token stale | pause adapter; reconnect with backoff; WeChat `-14` → notifyStart+relogin |
| Crash during a turn | in-memory turn queue recreated on restart; DSH session persistence keeps history for a resumed conversation |
| Long-poll disconnect | reconnect loop with backoff, resume from saved `get_updates_buf` cursor (WeChat) |

## 5. Dependencies & deployment

- Node >= 22.
- Runtime deps kept tiny: `qrcode-terminal` (QR), `ws` (Feishu gateway; may
  use built-in WebSocket), native `fetch`; platform SDKs optional per adapter.
- Deploy: `dsh plugin --profile imchat` → install as profile dependency →
  `dsh --profile imchat` (mirrors the `web` profile layout) OR mount into the
  running `web` profile's `cordis.patch.yml`. Primary: dedicated private
  profile where the plugin IS the agent driver (no browser surface).

## 6. Testing

- Unit: bridge core (session-key hashing, queue bounds, chunking).
- Adapter wire tests use mocked HTTP transport (WeChat/Feishu protocol shapes).
- E2E headless: `dsh --profile imchat --headless "say hi"` using a stub
  adapter to prove the create→followup→whenIdle→reply path.

## 7. Milestones

M1 bridge core + repo skeleton; headless demo harness (stub adapter).
M2 WeChat adapter (login + long-poll + send) — highest-value, matches the
   reference you linked.
M3 Feishu adapter.
M4 Matrix adapter.
M5 polish: docs, extras (media, whitelist, multi-model), tests.

## 8. Assumptions

- You want an **on-platform agent** (not a bridge into the web UI's agents).
- Personal always-on use. Single DSH process hosts all three adapters.
- The three platforms are independent installs; any subset is fine.

I recommend starting with the bridge core + a runnable headless/single-turn
demo (M1) to validate the DSH-agent-driving recipe end-to-end before porting
protocols — porting WeChat, Feishu, Matrix are each bounded, well-understood
jobs afterwards.
